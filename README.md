# HealthCraft – здоровье открытых репозиториев SourceCraft

HealthCraft оценивает состояние репозиториев SourceCraft по фактам из git, REST API и AppSec:
ставит оценку 0-100, объясняет, из чего она сложилась, и дает конкретные рекомендации с
ожидаемым эффектом. Все открытые репозитории платформы собраны в публичный рейтинг.

Кейс 18 хакатона «Лидеры цифровой трансформации» 2026, команда 10. Описание кейса от
организаторов – [docs/lct-case.md](docs/lct-case.md), техническое задание –
[docs/ТЗ-sourcecraft.pdf](docs/ТЗ-sourcecraft.pdf). Публичный стенд работал во время хакатона и после
его окончания выключен; сервис можно запустить у себя – см. [Быстрый старт](#быстрый-старт).

## Что умеет

| Возможность | Что это |
|---|---|
| Рейтинг | все открытые репозитории каталога SourceCraft: место и его изменение за сутки, HealthCraft Index, реакции, язык, дата активности, отметка проверки на накрутку (на место не влияет), ссылка на страницу в SourceCraft; сортировка по индексу, реакциям, активности, покрытию данными (доле веса категорий с данными) и имени; фильтры по языку, размеру кода, наличию CI и тематике (правила по словам адреса и описания, языку и зависимостям из манифестов, `src/api/topics.ts`; на оценку не влияет), поиск, переход к странице |
| Карточка репозитория | итоговая оценка, место в рейтинге и лига (TOP-10, TOP-100, TOP-1000), место среди похожих – тот же язык и размер кода («лучше 62% похожих»), вклад каждой категории, подметрики с исходными фактами, причины «нет данных», сильные и слабые стороны, история оценки по анализам; справочно, без влияния на оценку – стабильность CI в динамике, динамика создания и закрытия задач, ревью запросов на слияние и узкие места, карта владельцев файлов |
| 2 показателя | **HealthCraft Index** – 4 категории по данным, открытым для любого репозитория; **Repo Health Score** – 6 категорий, включая CI/CD и Безопасность, для зрителя с правами на эти данные |
| Рекомендации | проблема, почему это важно, факты, действие и ожидаемый эффект; эффект – пересчет модели с исправленным фактом, а не оценка на глаз. Режим «По шагам» – план до зоны «здоров»: исправления применяются одно поверх другого, после каждого шага виден итоговый индекс. Для 5 правил документации – готовые заготовки файлов: README, недостающие разделы README, CONTRIBUTING, CODEOWNERS по карте владельцев, LICENSE (MIT или Apache 2.0 на выбор автора) |
| Отчет | выгрузка оценки в Markdown и PDF – те же оценка, факты и рекомендации, что на карточке |
| Сравнение | 2-3 репозитория рядом по показателям и категориям |
| AI-обзор | текст о репозитории от языковой модели; каждая фраза ссылается на факт и проходит механическую проверку, непроверенный текст не показывается; на оценку не влияет. Запускает любой вошедший пользователь в пределах лимитов (по умолчанию 25 обзоров в сутки на человека); пароль снятия лимитов выдает администратор сервиса, он вводится в «Настройках» |
| Проверка на накрутку | признаки искусственной активности (роботы, всплески коммитов, ровные серии) кодом, вывод – языковой моделью |
| Периодический пересчет | сверка каталога раз в час, повторные анализы изменившихся репозиториев раз в сутки; при смене версии модели история пересчитывается из сохраненных фактов |
| Вход и свои репозитории | вход через Яндекс ID, разделы «Избранное» и «Мои репозитории» (список по токену), анализ своего репозитория; с персональным токеном SourceCraft – приватные репозитории и полный Repo Health Score |
| Публичный API и бейдж | JSON с индексом и категориями публичного репозитория без ключей, с CORS; SVG-бейдж для README своего репозитория – индекс и на выбор лига, зона, динамика и шкалы 4 категорий; бейдж закрытого репозитория – по ключу с карточки |
| Документация | раздел `/docs` сервиса: руководство, методика, устройство сервиса, развертывание; поиск по страницам и PDF-версия |

## Как получить оценку

- **Публичный репозиторий** уже в рейтинге: найдите его поиском или откройте
  `<адрес сервиса>/repo/<org>/<repo>`. Вход не нужен.
- **Свой или приватный репозиторий, полный Repo Health Score:**
  1. Войдите через Яндекс ID.
  2. В «Настройках» сохраните персональный токен доступа SourceCraft – по нему сервис проверяет
     ваши права на репозиторий, CI и AppSec. Репозитории, доступные токену, появятся в разделе
     «Мои репозитории» (в «Избранное» сами не попадают).
  3. Если репозитория нет в «Избранном», нажмите «Добавить» и введите `org/repo` или ссылку
     (или выберите из списка по токену) – первый анализ своего репозитория запустится сам. Для
     репозитория, который уже в списке, нажмите в его строке «Запустить анализ». Ход анализа виден в панели «Задания»; оценка
     появится в строке и на карточке.
- **Отчет и бейдж:** на карточке – выгрузка отчета в MD и PDF и готовый код бейджа для README.

## Как считается оценка

Оценка – взвешенное среднее баллов категорий, у которых есть данные. Категория без данных не
получает 0: она исключается, а ее вес делится между остальными (отсутствие данных не ухудшает
оценку).

| Категория | Вес в Repo Health Score | Вес в HealthCraft Index |
|---|---:|---:|
| Документация | 15 | 23 |
| Активность | 15 | 23 |
| Задачи | 15 | 23 |
| Состояние кода | 20 | 31 |
| CI/CD | 15 | – |
| Безопасность | 20 | – |

- Если данных меньше порога (доля веса категорий с данными ниже 0,4), оценка не выставляется.
- Репозиторий без кода получает 0.
- Критичные находки AppSec ограничивают Repo Health Score: открытый утекший секрет уровня
  `CRITICAL` – значением 49, любая другая открытая находка `CRITICAL` – значением 69. На HealthCraft Index потолки не влияют.
- Зоны: 70-100 «здоров», 40-69 «требует внимания», 0-39 «в зоне риска».
- Рейтинг сортируется по HealthCraft Index: результаты CI и находки AppSec платформа отдает только
  участникам репозитория, поэтому в публичный рейтинг они не входят.

Формула, подметрики, «нет данных», рекомендации и защита от накрутки – раздел «Методика оценки»
документации (`/docs` сервиса), в репозитории – [docs/guide/method/](docs/guide/method/)
(модель `4.7.0-hci`).

## Принципы

- **Оценку считает код.** Баллы – детерминированные функции фактов: одинаковые факты дают
  одинаковую оценку, версия модели записана у каждой оценки. Языковая модель пишет только текст.
- **«Нет данных» не равно «плохо».** Каждый факт в одном из 3 состояний: есть данные, нет данных,
  источник ответил ошибкой. Незнание не штрафуется, подтвержденное отсутствие (нет лицензии,
  задачи не ведутся) – это данные.
- **Код не храним.** Репозиторий клонируется во временный каталог, из клона извлекаются факты,
  клон удаляется. В базе – факты (счетчики, признаки, даты, агрегаты AppSec без кода и путей),
  история коммитов (хеш, имена и почта авторов, даты), оценки и рекомендации, проверенные
  AI-тексты, пользователи и избранное, хеши сессий и зашифрованные токены. Исходный код не
  хранится; подробнее – [docs/guide/data/sources.md](docs/guide/data/sources.md#privatnost).
- **Безопасность – только данные AppSec SourceCraft**, собственного сканирования нет.
- **Закрытое – только тем, у кого есть права.** Данные CI, AppSec и приватных репозиториев видит
  только зритель, чей токен SourceCraft дает к ним доступ; публичный API отдает только публичные
  репозитории рейтинга.

## Архитектура

```
                    браузер, README с бейджем
                               |
                   caddy: HTTPS, заголовки защиты
                               |
    +--------------------------+     +---------------------------------+
    | web                      |     | rating                          |
    | сайт и API, вход Я ID,   |     | обход каталога, плановые сканы, |
    | пользовательские сканы,  |     | пересчет оценок, AI для топа    |
    | AI-обзоры и проверки     |     | рейтинга                        |
    +------------+-------------+     +----------------+----------------+
                 |                                    |
                 +------> SQLite (WAL): факты, <------+
                          оценки, очередь заявок

  внешние сервисы: SourceCraft REST API, AppSec API, git-клоны (временный каталог),
                   Яндекс ID (OAuth), Yandex AI Studio (Qwen3.6-35B-A3B)
```

**Путь данных:** заявка на скан → клон git и запросы к REST и AppSec → факты в БД → оценка и
рекомендации кодом → (по запросу) AI-текст через валидатор фактов. Отчеты MD и PDF, карточка и
публичный API читают одни и те же сохраненные данные.

**Роли процесса** задает `PROCESS_ROLE`; образ и код у ролей общие.

| Роль | Что делает |
|---|---|
| `web` | сайт и API, пользовательские сканы, AI-обзоры и проверки на накрутку |
| `rating` | сверка каталога, плановые сканы рейтинга, суточный снимок мест рейтинга, стартовый пересчет, AI для топа рейтинга (`AI_TOP_AUTO`, по умолчанию выключен) |
| `all` | все сразу в одном процессе – режим разработки, значение по умолчанию |

Заявки лежат в очереди в той же БД и берутся с арендой: при штатной остановке процесс возвращает
свои заявки в очередь, при аварийной их подбирают после истечения аренды. Подробнее –
[docs/guide/ops/architecture.md](docs/guide/ops/architecture.md).

**Стек:** Bun 1.4.2 и TypeScript (strict), SQLite (`bun:sqlite`), React 19 и Gravity UI
(`@gravity-ui/uikit` 7.49.0), pdfmake 0.3.11 для PDF, языковая модель Qwen3.6-35B-A3B в Yandex AI Studio или z.ai – по настройке `LLM_PROVIDER`,
Docker Compose и Caddy 2.10, CI GitHub Actions.

## Быстрый старт

### Что нужно

| Для чего | Что |
|---|---|
| Запуск из исходников | [Bun](https://bun.sh) 1.4.2, git 2.31 или новее |
| Запуск в контейнерах | Docker с Compose v2 |
| Данные | персональный токен SourceCraft (`SOURCECRAFT_TOKEN`) – без него API SourceCraft отвечает 401; [как выпустить токен](https://sourcecraft.dev/portal/docs/ru/sourcecraft/security/pat) |
| Вход и AI (необязательно) | для входа – OAuth-приложение Яндекс ID и `APP_SECRET`, для AI – API-ключ Yandex AI Studio и каталог Yandex Cloud |

### Из исходников

Команды – для bash (Linux, macOS, WSL).

```bash
git clone https://github.com/exsec-dev/case-18-repo-health-score-team-10.git
cd case-18-repo-health-score-team-10
bun install --frozen-lockfile
cp .env.example .env        # вписать SOURCECRAFT_TOKEN, остальное по желанию
bun start                   # http://localhost:8418, интерфейс в dev-сборке с HMR
```

Проверка, что сервис жив:

```bash
curl http://localhost:8418/api/health
```

БД SQLite создается сама в `data/`. Первый обход каталога начинается через 5 минут после старта:
сервис ставит сканы в очередь, начиная с самых заметных репозиториев (по реакциям), и рейтинг
наполняется по мере сканов. Проанализировать 1 репозиторий сразу:

```bash
bun scripts/scan.ts <org>/<repo>
```

`NODE_ENV=production bun start` – то же с минифицированной сборкой интерфейса.

### В контейнерах

Общий образ ([`Dockerfile`](Dockerfile)) для обеих ролей, прокси с HTTPS – [`deploy/compose.yaml`](deploy/compose.yaml):

| Контейнер | Роль |
|---|---|
| `web` | `PROCESS_ROLE=web` |
| `rating` | `PROCESS_ROLE=rating`; стартует после здорового `web` и уступает ему процессор |
| `caddy` | HTTPS (Let's Encrypt), заголовки защиты, адрес клиента для лимитов; единственный контейнер с портами наружу |

Оба процесса работают с одной SQLite на общем томе. Каталог данных задает `HC_DIR`
(по умолчанию `/srv/healthcraft`): там `.env`, `data/` (БД) и `tmp/` (временные клоны).
Контейнеры сервиса работают от пользователя `bun` (uid 1000) без root и без capabilities,
поэтому `data/` и `tmp/` на хосте должны принадлежать uid 1000: `deploy/deploy.sh` делает это
сам, если на ВМ есть root или `sudo` без пароля; локально – строка с `chown` ниже, до первого
запуска (одноразовый контейнер, `sudo` не нужен). Команды – для bash в Linux, macOS или WSL;
Git Bash в Windows подменяет пути в аргументах `docker` и не подходит.

```bash
mkdir -p .stand && cp .env.example .stand/.env    # вписать токен; без SITE_ADDRESS прокси работает по HTTP
echo "HC_DIR=$PWD/.stand" >> .stand/.env
docker run --rm -v "$PWD/.stand:/stand" busybox:1.37 sh -c "mkdir -p /stand/data /stand/tmp/web /stand/tmp/rating && chown -R 1000:1000 /stand/data /stand/tmp"
HTTP_PORT=8080 docker compose --env-file .stand/.env -f deploy/compose.yaml up -d --build
curl http://localhost:8080/api/health             # через несколько секунд – "ok": true
```

Если на машине занят и порт 443, добавьте `HTTPS_PORT=8443` перед `docker compose`. Остановить:

```bash
docker compose --env-file .stand/.env -f deploy/compose.yaml down
```

### Сборка

Отдельного шага сборки нет: Bun собирает интерфейс (React и Gravity UI) из импорта
`src/web/index.html` при старте сервера, поэтому `bun start` поднимает сразу и API, и интерфейс.
Режим сборки задает `NODE_ENV`:

| Команда | Что собирается |
|---|---|
| `bun start` | dev-сборка с HMR; страницы `/docs` перечитываются с диска при каждом запросе |
| `NODE_ENV=production bun start` | минифицированная сборка без HMR; документация читается один раз на старте. Так работает образ контейнера |

Проверка типов – `tsc --noEmit` по `src/`, `scripts/` и `tests/` (см. [`tsconfig.json`](tsconfig.json)),
ошибок быть не должно:

```bash
bun run tsc
```

Образ контейнера собирается из корня репозитория по [`Dockerfile`](Dockerfile): база `oven/bun:1.4.2`
плюс git, зависимости по lock-файлу без dev-пакетов, в образ попадают `src/`, `prompts/`, `docs/guide/` и
`tsconfig.json`; вход через `deploy/entrypoint.sh` (чистит осиротевшие клоны и проверяет тома).
Раздел «В контейнерах» собирает его через `docker compose … --build`; вручную:

```bash
docker build -t healthcraft .
```

### Тесты

Тесты лежат в `tests/*.test.ts` и запускаются `bun test`. Те же команды выполняет CI GitHub Actions на
каждый push и pull request – [`.github/workflows/ci.yml`](.github/workflows/ci.yml):

```bash
bun run tsc
bun test --timeout 30000                 # все тесты
bun test tests/score.test.ts             # один файл
bun test -t "killActiveClones"           # тесты по имени
sh scripts/ci-test.sh                    # как в CI: SQLite без fsync, временные БД в /dev/shm
```

Тесты работают на временных БД и не обращаются к внешним сервисам: SourceCraft, Яндекс ID и
языковая модель подменяются локальными моками, токен в `.env` не нужен. Лимит 30 с на тест
задан потому, что на медленном диске тесты с временной БД идут 4–7 с и дефолтных 5 с не хватает.

Тестам нужны git, символьные ссылки и `setsid`, поэтому запускайте их в Linux или WSL. В Windows
около десятка тестов падает: группы `setsid` у клонов, символьные ссылки, остановка сервера по SIGTERM
(остальные 2000 проходят). В macOS команды `setsid` нет.
Золотые отчеты в `tests/fixtures/report/` сравниваются побайтно; после осознанного изменения
отчета перегенерируйте их и просмотрите глазами:

```bash
bun scripts/report-goldens.ts
```

## Переменные окружения

Все настройки – переменные окружения. Полный список с пояснениями и значениями по умолчанию
(бюджеты скана, лимиты очереди и AI, интервалы планировщика) – [`.env.example`](.env.example).
Ключевые:

| Переменная | Когда нужна | Что задает |
|---|---|---|
| `SOURCECRAFT_TOKEN` | всегда | токен SourceCraft API: каталог, REST, AppSec |
| `APP_SECRET` | вход | ключ подписи сессий и шифрования токенов пользователей, не короче 32 символов; без него вход выключен |
| `YA_CLIENT_ID`, `YA_CLIENT_SECRET` | вход | OAuth-приложение Яндекс ID; без них `/auth/ya` отвечает 503 |
| `YA_REDIRECT_URI` | вход | адрес возврата после входа, по умолчанию `http://localhost:8418/auth/ya/callback` |
| `LLM_PROVIDER`, `MAIN_MODEL` | AI | провайдер `yandex` – Yandex AI Studio (по умолчанию) или `zai` (ключ – `ZAI_API_KEY`) и модель: по умолчанию `qwen3.6-35b-a3b`; провайдер один, автоматического переключения нет |
| `YAGPT_API_KEY`, `YAGPT_FOLDER_ID` | AI | API-ключ Yandex AI Studio и каталог Yandex Cloud; без них AI-обзоров нет |
| `AI_UNLOCK_PASSWORD` | по желанию | пароль снятия лимитов AI, выдает администратор сервиса; не короче 20 символов, требует `APP_SECRET`; пусто – функции нет |
| `AI_TOP_AUTO` | по желанию | `1` – автоматически готовить AI-обзор и проверку для топа рейтинга после нового скана (выключено по умолчанию) |
| `AI_TOP_AUTO_SIZE` | по желанию | сколько первых мест рейтинга входит в этот топ (10) |
| `LLM_CALL_TIMEOUT_MS` | по желанию | общий предел одного вызова модели вместе с ответом, мс (180000) |
| `PORT`, `DATA_DIR` | из исходников | порт (8418) и каталог БД (`data`) |
| `PROCESS_ROLE` | из исходников | `all` (по умолчанию), `web` или `rating` |
| `PUBLIC_BASE_URL` | стенд | публичный адрес для кода бейджа; по умолчанию – адрес из `YA_REDIRECT_URI` |
| `SITE_ADDRESS`, `CANONICAL_HOST` | стенд | домены для HTTPS в Caddy и основной домен, на который переадресуются остальные |
| `STAND_IP` | стенд | IP машины: запрос `http://IP` переадресуется на основной домен |
| `HC_DIR`, `HTTP_PORT`, `HTTPS_PORT` | контейнеры | каталог стенда и порты прокси на машине |

`SITE_ADDRESS`, `CANONICAL_HOST`, `STAND_IP`, `HC_DIR`, `HTTP_PORT`, `HTTPS_PORT` читает `deploy/compose.yaml`, а не
сервис; в `.env.example` они собраны в блоке «Стенд в контейнерах». В контейнерах `PORT`,
`DATA_DIR`, `PROCESS_ROLE` и `SCAN_MIN_FREE_MB` в `.env` не задают: их задают `deploy/compose.yaml`
и образ (`DATA_DIR` из `.env` увел бы базу с тома `/data`). Остальные переменные –
[docs/guide/ops/deploy.md](docs/guide/ops/deploy.md#nastroyki).

## Развертывание

Стенд – ВМ Compute Cloud: Ubuntu 24.04, 4 vCPU, 8 ГБ памяти, SSD 64 ГБ, статический IP; группа
безопасности пропускает входящие TCP 22, 80, 443.

1. **Подготовка ВМ** (однократно): Docker, `sqlite3` и `zstd` для резервных копий, пользователь в
   группе `docker`, каталог стенда, подкачка 4 ГБ:
   ```bash
   sudo apt update && sudo apt install -y docker.io docker-compose-v2 sqlite3 zstd
   sudo usermod -aG docker "$USER"            # действует после повторного входа по SSH
   sudo install -d -o "$USER" /srv/healthcraft
   sudo fallocate -l 4G /swapfile && sudo chmod 600 /swapfile
   sudo mkswap /swapfile && sudo swapon /swapfile
   echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab
   ```
2. **Секреты** (однократно): `/srv/healthcraft/.env` с правами `600` – переменные из `.env.example`
   плюс адрес стенда:
   ```ini
   SITE_ADDRESS=example.com, www.example.com
   CANONICAL_HOST=example.com
   PUBLIC_BASE_URL=https://example.com
   YA_REDIRECT_URI=https://example.com/auth/ya/callback
   ```
   A-записи домена указывают на IP ВМ; `YA_REDIRECT_URI` добавляется в OAuth-приложение Яндекс ID.
3. **Выкладка** (с машины разработчика, каждый раз):
   ```bash
   deploy/deploy.sh healthcraft@<IP ВМ>
   ```
   Скрипт ([`deploy/deploy.sh`](deploy/deploy.sh)) везет код закоммиченного `HEAD` без `.env` и
   данных, собирает образ на ВМ и перезапускает контейнеры. Прошлая версия кода остается в
   `app.prev`; откат – выкладка нужного коммита. Ключ SSH – `HC_SSH_KEY` (по умолчанию
   `~/.ssh/healthcraft-stand`). Сертификат HTTPS Caddy выпускает и продлевает сам.
4. **Резервные копии:** [`deploy/backup.sh`](deploy/backup.sh) раз в сутки делает копию
   работающей БД (`VACUUM INTO`), проверяет целостность, сжимает и хранит 3 последние копии в
   `/srv/healthcraft/backups`. Копии лежат на том же диске: от ошибки в данных защищают, от
   потери диска – нет. Запуск по расписанию – строка в `crontab -e` на ВМ, например в 01:30 UTC
   (04:30 МСК). Журнал пишется рядом с `backups/`, а не в него: каталог `backups/` создает сам
   скрипт, а оболочка открывает файл журнала раньше:
   ```bash
   30 1 * * * /srv/healthcraft/app/deploy/backup.sh >> /srv/healthcraft/backup.log 2>&1
   ```

**Состояние стенда** – `GET /api/health`. HTTP-статус всегда 200, смотреть нужно поле `ok` в
теле: оно вычисляется по живости очередей, обхода каталога и пересчета, а `reasons` перечисляет,
что не так. Healthcheck контейнера `web` проверяет только, что процесс отвечает, поэтому `web`
остается healthy и при `"ok": false` – например, пока идет пересчет оценок после смены модели.
Так задумано: перезапуск контейнера такие состояния не исправляет, а `rating` стартует только
после healthy `web`. Состояние сервиса отслеживают по полю `ok`.

## Публичный API и бейдж

Без авторизации, только для публичных репозиториев рейтинга. Приватный, выведенный из рейтинга и
несуществующий репозиторий неотличимы – 404. Ответ 200 кэшируется 5 мин (`max-age=300`), лимит –
120 запросов в минуту с 1 IP, общий для JSON и бейджа (сверх лимита – 429 с `Retry-After: 60`).
Все ответы `/api/v1/*`, включая ошибки, несут `Access-Control-Allow-Origin: *`: JSON можно
читать из браузера с любого сайта.

| Маршрут | Ответ |
|---|---|
| `GET /api/v1/repos/{org}/{repo}` | JSON: `healthcraftIndex`, `indexCoverage`, баллы 4 публичных категорий (`categories`), `modelVersion`, `scannedAt`, `headSha`, `codeEmpty` (в репозитории нет кода), а также `org`, `repo`, `title`, `language`, `likes` |
| `GET /api/v1/repos/{org}/{repo}/badge.svg` | SVG-бейдж «HealthCraft Index»: число и цвет зоны, без оценки – `n/a` серым; `?show=rank,word,delta,cats` – с лигой места, словом зоны, изменением с прошлого анализа и шкалами 4 категорий под индексом, `?category=<категория>` – балл 1 категории, `?key=` – бейдж закрытого репозитория по ключу с карточки; прежний `?style=rank` работает как `?show=rank` |

Бейдж в README репозитория (готовый код для своего репозитория дает кнопка на карточке):

```markdown
[![HealthCraft Index](https://<адрес сервиса>/api/v1/repos/<org>/<repo>/badge.svg)](https://<адрес сервиса>/repo/<org>/<repo>)
```

Интерфейс работает через тот же сервер: `GET /api/repos` (рейтинг),
`GET /api/repos/{org}/{repo}` (карточка), `…/report.md` и `…/report.pdf` (отчет),
`…/ai-status` (идут ли обзор и проверка: легкий опрос страницы, в лимит открытий карточки не входит),
`GET /api/compare?r={org}/{repo}&r=…` (сравнение), `…/fix/{ruleId}` (заготовка файла по
рекомендации), `GET /api/meta` (версия модели и число оцененных), `GET /api/docs` и
`/docs/healthcraft.pdf` (документация и ее PDF-версия). Их ответ может зависеть от прав зрителя и
меняться вместе с интерфейсом – для внешних интеграций предназначен `/api/v1`. Подробнее –
[docs/guide/guide/badge-api.md](docs/guide/guide/badge-api.md).
