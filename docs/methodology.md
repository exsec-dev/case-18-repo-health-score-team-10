# Методика оценки здоровья репозитория — HealthCraft

**Версия модели:** `4.3.1-hci` · **версия сборщика данных:** 4 · 26.09.2026

Документ описывает, как сервис считает оценку репозитория SourceCraft: какие
данные собирает, как превращает их в баллы, что делает при отсутствии данных,
как строит рекомендации и где у методики границы. Все числа ниже — константы
кода (`src/score/model.ts`); расчет детерминирован: одинаковые факты дают
одинаковую оценку. История выработки методики (драфты, аудиты, решения) — в
`reports/` (указатели в конце документа).

## 1. Два показателя

| Показатель | Категории | Где виден | Зачем |
|---|---|---|---|
| **HealthCraft Index** | Документация, Активность, Задачи, Состояние кода | рейтинг, карточка, значок, публичный API | публичная оценка по данным, открытым для любого репозитория |
| **Repo Health Score** | те же 4 + CI/CD и Безопасность | карточка и отчет зрителя с правами на CI и AppSec | полная оценка для участников репозитория |

CI/CD и Безопасность в публичный рейтинг не входят: результаты запусков CI и
находки AppSec платформа отдает только участникам репозитория, а организаторы
(Q&A №1) указали не вкладывать их в общий рейтинг.

**Итог** — взвешенное среднее категорий с данными:

`итог = Σ(балл категории × вес) / Σ(вес категорий с данными)`

| Категория | Вес в Repo Health Score | Вес в HealthCraft Index |
|---|---:|---:|
| Документация | 15 | 23 |
| CI/CD | 15 | — |
| Безопасность | 20 | — |
| Активность | 15 | 23 |
| Задачи | 15 | 23 |
| Состояние кода | 20 | 31 |

Веса полного показателя — пример весов ТЗ §3.2. Веса индекса — те же веса,
пересчитанные на массу четырех публичных категорий (65 → 100) и округленные до
целых (15/65 ≈ 23, 20/65 ≈ 31).

**Правила итога:**

- **Категория без данных** не получает 0: она исключается, ее вес делится между
  остальными пропорционально (отсутствие данных не ухудшает оценку, ТЗ §3.2).
- **Порог объема данных:** если доля номинального веса категорий с данными ниже
  **0,4** (для индекса — от массы 65, для полного — от 100), итог не выставляется:
  «оценки нет — данных недостаточно». Для индекса две любые публичные категории
  порог проходят (30 из 65 = 0,46), одна — нет.
- **Кода нет — итог 0** (Q&A №13): репозиторий без коммитов, без файлов или
  только с документами, лицензиями, картинками, архивами. Это данные «проекта
  нет», а не отсутствие данных. Категория «Состояние кода» при этом получает
  **0 с названной причиной** (4.3.1; в 4.3.0 была «нет данных»): отсутствие
  кода — подтвержденный факт о репозитории, а не незнание.
- **Утекший критичный секрет** (AppSec, тип SECRETS, severity CRITICAL, группа
  открыта) — Repo Health Score не выше **49**.
- **Зоны:** 70-100 «здоров», 40-69 «требует внимания», 0-39 «в зоне риска» — по
  округленному баллу.

## 2. Принципы

1. **Считает только код.** Баллы — детерминированные функции фактов. Языковая
   модель пишет только текст описания по уже посчитанным фактам и на оценку не
   влияет.
2. **Три состояния данных:** есть данные, нет данных, источник ответил ошибкой.
   «Плохо» и «неизвестно» различаются везде: в формуле, на карточке, в отчете.
3. **Подтвержденное отсутствие — данные.** Нет лицензии, 0 открытых задач при
   закрытых, 0 пометок TODO, 0 запусков CI при видимых запусках — это факты с
   оценкой, а не пропуск.
4. **Категория получает число только при своей основной (якорной) метрике.**
   Второстепенная метрика одна не несет категорию: без истории коммитов нет
   «Активности», без строк кода нет «Состояния кода», без плотности находок и
   доли закрытых нет «Безопасности».
5. **Малая выборка сжимается, а не усиливается.** Одна закрытая задача не делает
   трекер образцовым, одна строка кода — «Состояние кода» идеальным.
6. **Улучшение факта не снижает оценку** (монотонность). Проверяется
   автоматически сотнями тысяч случайных мутаций фактов (§9).
7. **Объективно измеримое — инструментами.** Безопасность — только данные AppSec
   SourceCraft, своего сканирования нет (ТЗ §11.6).

## 3. Источники и сбор данных

| Канал | Что дает | Доступ |
|---|---|---|
| **Клон git** (bare, во временном каталоге; после извлечения фактов удаляется — исходный код не хранится) | история коммитов, файлы в корне, README, лицензия, CONTRIBUTING, CODEOWNERS, `.sourcecraft/ci.yaml`, строки кода, пометки TODO и их возраст | публичные репозитории — всем; приватные — по токену участника |
| **REST API SourceCraft** | задачи (открытые, в работе, закрытые), комментарии, запросы на слияние, релизы, участники, запуски CI | запуски CI — только участникам |
| **AppSec API SourceCraft** | группы находок последнего завершенного скана: серьезность, статус, тип (секреты) | только участникам с правом AppSec |

**Правила извлечения (сборщик 4):**

- **Файлы кода** — все файлы, кроме документов (`.md`, `.txt`, `.rst`, …),
  лицензий, служебных файлов git, lock-файлов, картинок, архивов, офисных
  документов, медиа и собранных бинарников. Файл с «кодовым» именем, но
  бинарным содержимым — тоже не код.
- **Строки кода** — строки текстовых файлов кода (строка без завершающего
  перевода строки — тоже строка). Файлы больше лимита текста помечаются как
  непрочитанные.
- **Пометки техдолга** — `TODO`, `FIXME`, `HACK`, `XXX` без учета регистра, только
  первым словом комментария (`//`, `/*`, `<!--` — где угодно; `#`, `--`, `;`, `%`,
  `'`, `*`, `REM` — в начале строки). Считаются только в файлах кода **вне
  тестов** (4.3.1): у сканеров пометок тесты состоят из намеренных маркеров, и
  счетчик переставал быть про код (repo-vitals: 196 пометок при 37 в
  комментариях кода); число пропущенных в тестах маркеров хранится в факте
  (`test_markers`). Возраст — дата автора коммита строки (`git blame`);
  старые — старше 180 дней (пример ТЗ §3.4).
- **Файлы тестов** — непустые файлы кода в каталогах `test/`, `tests/`,
  `__tests__/`, `spec/`, `specs/` или с именами `test_*`, `*_test.*`, `*.test.*`,
  `*.spec.*`; данные тестов (`fixtures/`, `testdata/`, `mocks/`, `data/` внутри них) —
  не тесты.
- **Лицензия, CONTRIBUTING, CODEOWNERS** — файл в корне с не менее чем 16
  непробельными символами; лицензия распознается и как `LICENSE-*`, `COPYING*`,
  `UNLICENSE`, каталог `LICENSES/`.
- **Разделы README** «установка», «сборка», «тесты» — по заголовкам (русский и
  английский словарь), только если под заголовком есть текст или блок кода.
- **Задачи:** открытые — статусы `open` и `in_progress`; задачи, закрытые быстрее
  часа после создания, в оценку не входят (защита от «открыл и сразу закрыл»);
  зависшая — открытая без обновлений 90 дней.
- **Запуски CI** — упорядочиваются по дате начала; доля успеха — по завершенным
  (`success` против `failed`/`timeout`); отмененные, пропущенные, идущие — вне
  доли. Каждый статус перечня спеки обрабатывается своей веткой.
- **AppSec** — только группы в открытых статусах (`OPEN`, `TRIAGE_IN_PROGRESS`,
  `TRIAGED_TP`, `FIX_IN_PROGRESS`); закрытые и ложные не штрафуют.
- **Релизы** — только опубликованные; **запросы на слияние** — всех статусов.

## 4. Категории

Внутри категории балл — взвешенное среднее подметрик с данными; подметрика без
данных исключается с перераспределением веса. Анкеры — кусочно-линейные таблицы
«значение → балл 0-1», за крайними точками — плоско.

### 4.1 Документация

| Подметрика | Вес | Как считается |
|---|---:|---|
| README | 0,45 | наличие 0,3 + качество 0,7; качество = размер 0,5 (0 Б → 0, 500 Б → 0,2, 2 КБ → 0,6, 20 КБ → 1) + разделы установка/сборка/тесты 0,5 (доля найденных) |
| Лицензия | 0,25 | есть — 1, нет — 0 |
| CONTRIBUTING | 0,15 | есть — 1, нет — 0 |
| CODEOWNERS | 0,15 | есть — 1, нет — 0 |

### 4.2 Активность

Коммиты делятся на человеческие и служебные (§5); в подметрики идут только
человеческие, по дате автора.

| Подметрика | Вес | Анкеры |
|---|---:|---|
| Свежесть последнего коммита человека | 0,35 | 1 мес → 1, 6 → 0,7, 12 → 0,45, 24 → 0,1; людей в истории нет — 0 |
| Частота (коммитов в месяц за 90 дней) | 0,25 | `min(1, log(x+1)/log 31)`: 30 в месяц — 1 |
| Авторы-люди | 0,2 | 1 → 0,2, 10 → 0,6, 100 → 1 (лог) |
| Запросы на слияние за 90 дней | 0,1 | 0 → 0,2, 5 → 0,6, 30 → 1 (лог) |
| Релизы за 12 месяцев | 0,1 | 0 → 0,2, 2 → 0,6, 6 → 1 (лог) |

Якорь — свежесть или частота: без прочитанной истории коммитов категория «нет
данных». Справочно, без веса: bus factor, коммиты за 90 и 365 дней, доля
синхронизаций, всплески.

**Review и bottlenecks запросов на слияние (справочно, без веса; ЗН-2 ТЗ §7,
В5.5 тур 2).** Выборка — до 10 последних запросов (по дате создания) из уже
полученного списка, без черновиков: черновик на ревью не отправлен.
На каждый — 1 страница комментариев и 1 страница ревьюеров: **не больше 20
запросов на репозиторий** (без запросов на слияние — 0), меньше выборки
комментариев задач. Ответ ревьюера — первый опубликованный неудаленный
комментарий не автора или решение `approve`, `trust`, `block` не автора
(`abstain` — отказ от ревью, ответом не считается; комментарии AppSec — не
ответ человека).

| Показатель | Как считается |
|---|---|
| Время до первого ответа на PR | медиана часов от создания до ответа ревьюера по запросам выборки с ответом |
| PR без ответа дольше 3 дней | открытые запросы выборки без ответа старше 72 ч — «N из M открытых» (`merging` уже сливается и не ждет) |
| Комментариев ревью на PR | медиана числа комментариев не автора по выборке; у запроса с полной страницей комментариев — «не меньше» |
| Время до слияния PR | медиана часов по до 50 последним слитым запросам списка; даты слияния API не отдает — приближение датой последнего изменения запроса (оговорка на карточке и в отчете) |

Запросов на слияние нет — данные «PR не используются», а не «нет данных»;
сбой любого запроса выборки — «нет данных» (урезанная выборка за данные не
выдается). Статусы запроса, решения ревью и типы комментариев спеки
обрабатываются каждое своей веткой, неизвестное — названо в факте.

### 4.3 Задачи

- **Трекер не ведется** (0 открытых и 0 закрытых) — балл **6**: вычислимый
  минимум категории (все подметрики на худших узлах). Любой ведущийся трекер
  получает не меньше.
- Иначе:

| Подметрика | Вес | Анкеры |
|---|---:|---|
| Доля зависших среди открытых | 0,3 | 0 → 1, 0,5 → 0,5, 1 → 0,1; открытых нет при закрытых — 0 (данные) |
| Медиана времени закрытия, дни | 0,3 | 2 → 1, 7 → 0,85, 30 → 0,5, 90 → 0,2, 180 → 0; ни одна не закрыта — 0 |
| Доля решенных `закрытые / (открытые + закрытые)` | 0,3 | 0 → 0,1, 0,5 → 0,55, 0,9 → 0,95, 1 → 1 |
| Первый ответ, часы (медиана по свежим открытым) | 0,1 | 24 → 1, 72 → 0,7, 168 → 0,4, 720 → 0; без ответа дольше 30 дней — 720 ч |

- **Сжатие малой выборки:** `балл = 6 + (сырой − 6) × min(1, N/10)`, где N —
  закрытые задачи, прожившие не меньше часа. До 10 таких задач балл тянется к
  минимуму трекера; открытые задачи выборку не наращивают.

### 4.4 Состояние кода

| Подметрика | Вес | Анкеры |
|---|---:|---|
| Плотность пометок на 1000 строк кода | 0,35 | 0 → 1, 2 → 0,8, 10 → 0,5, 30 → 0,25, 60 → 0 |
| Доля старых пометок (старше 180 дней) | 0,25 | 0 → 1, 0,3 → 0,7, 0,8 → 0,1; доля считается от не менее 5 пометок; пометок нет — 0 (данные, «старых нет») |
| Тесты (доля файлов тестов среди файлов кода) | 0,3 | 0,05 → 0,5, 0,15 → 0,8, 0,3 → 1 — **бонус**: входит в балл, только если поднимает его; тестов нет — подметрика вне расчета |
| Порядок в корне (записей в корне) | 0,1 | 15 → 1, 40 → 0,6, 100 → 0,2 |

- Якорь — плотность пометок: нет прочитанных строк кода — «нет данных»;
  **кода в репозитории нет** (нет файлов кода, или файлы кода пустые) — балл
  категории **0** с названной причиной (4.3.1), это данные, а не незнание.
  Пометки считаются только в коде вне тестов (§3).
- **Сжатие малого кода (только вниз):** `балл = min(сырой, 50 + (сырой − 50) ×
  min(1, строк/200))`. Хороший код на нескольких строках получает около 50, а не
  100; плохой малый код к 50 не подтягивается.

**Карта владельцев файлов (справочно, без веса; ЗН-2 ТЗ §7, В5.5 тур 2).**
Из клона на время анализа (в хранилище — только агрегаты): коммиты людей за
365 дней по дате автора, без слияний, без роботов и сгенерированных всплесков
(§5, по sha). Изменение — «коммит тронул файл кода» (§3: без документов,
lock-файлов, картинок), так что большой сгенерированный дифф не перевешивает.
Для каждого верхнеуровневого каталога (файлы корня — отдельной строкой) —
главный автор, его доля изменений и число авторов; в карте — до 10 самых
изменяемых каталогов. Итог — **доля изменений в каталогах с единственным
владельцем** (главный автор сделал не меньше 80% изменений каталога) как
сигнал bottleneck знаний. Человек различается по email, но в хранилище и на
экран идет только отображаемое имя из git — email никогда (имя в форме адреса
маскируется), как у bus factor. Бюджет обхода — 5000 последних коммитов и
100 000 изменений; обрезка и укороченная история деградационного клона
помечаются в факте и в сноске к карте. Рядом с картой — есть ли CODEOWNERS.
Категория выбрана «Состояние кода»: карта описывает участки кода, а
людская сторона (bus factor) уже в «Активности».

### 4.5 CI/CD (только полный показатель)

- **Запуски не видны** (нет прав) — «нет данных» при любом `ci.yaml`.
- **Запуски видны:**
  - нет `.sourcecraft/ci.yaml` или в нем нет задачи с командой — **0**;
  - `ci.yaml` не удалось разобрать — «нет данных»;
  - видимых запусков 0 или все старше года — «CI не запускался»: конфигурация
    засчитана, доля успеха 0 → балл 40;
  - все запуски еще идут — «нет данных»;
  - иначе:

| Подметрика | Вес | Анкеры |
|---|---:|---|
| Конфигурация со шагами | 0,3 | есть — 1 |
| Доля успешных запусков, взвешенная по свежести | 0,45 | 0 → 0, 0,5 → 0,4, 0,9 → 0,85, 1 → 1 |
| Медианная длительность успешного запуска, мин | 0,25 | 2 → 1, 5 → 0,8, 15 → 0,5, 30 → 0,2 |

Веса запусков по возрасту: до 3 дней — 30, до 13 — 20, до 43 — 10, до 133 — 5, до
363 — 2,5, старше — 0 (свежий провал весит больше старого успеха).

### 4.6 Безопасность (только полный показатель)

| Подметрика | Вес | Как считается |
|---|---:|---|
| Плотность открытых находок на 10 тыс. строк кода | 0,5 | `8·critical + 4·high + 2·medium + 1·low`; 0 → 1, 2 → 0,8, 5 → 0,6, 10 → 0,4, 20 → 0,1; находок нет — 1 |
| Доля закрытых находок | 0,3 | анкеры как у доли решенных задач |
| Критичные секреты | 0,2 | нет — 1, есть — 0 (и потолок итога 49) |

- **Потолок категории:** открытая critical — не выше **40**, открытая high — не
  выше **69**: одна тяжелая находка не растворяется в размере кода.
- Нет данных AppSec (нет права, нет завершенного скана) — «нет данных»; скан без
  находок — данные (Q&A №15).

## 5. Роботы и синхронизации

- **Робот** — автор с маркером в имени или адресе (`[bot]`, `-bot`, `dependabot`,
  `renovate`, `allcontributors`, локальная часть на `bot`) или служебный адрес
  (`noreply@github.com`, домен `noreply.github.com`). Приватная почта GitHub
  (`…@users.noreply.github.com`) — человек.
- **Сгенерированный всплеск** — 10 и более коммитов в окне 2 секунд по дате
  коммиттера, у которых и даты автора в том же окне. Такие коммиты исключаются из
  свежести, частоты и авторов (1000 пустых коммитов за секунду не двигают оценку).
- **Ребейз и импорт зеркала** (даты коммиттера сжаты, даты автора разнесены) —
  обычная история по датам автора: происхождение репозитория на оценку не влияет
  (Q&A №10).

## 6. Рекомендации

Детерминированный движок правил: каждая рекомендация — проблема, почему это
важно, факты, действие и ожидаемый эффект.

- **Эффект** — реальный пересчет: к фактам применяется исправление, модель
  считается заново, разница называется числом в шкале своего показателя
  (публичные правила — HealthCraft Index, CI и AppSec — Repo Health Score). Где
  числа нет (категория откроется, эффект не выражается в баллах), эффект назван
  словами.
- **Порядок:** сначала серьезные (утекшие секреты и критичные находки, красный
  CI), затем исправления по величине эффекта, затем открывающие категорию, затем
  прочие.
- **Условия правил — те же, что у балла:** совет по категории выдается только
  если категория оценена; обещание «повысит балл» дается только если пересчет его
  подтверждает. Совет, которому пересчет дает **нулевой или отрицательный
  эффект, не выводится вовсе** (4.3.1): строки вида «+0,0 к показателю» в выдаче
  нет, в том числе при потолке 49 за секреты и при итоге NULL.
- Репозиторию без кода дается один совет — добавить код.

## 7. Нет данных: причины

Каждое «нет данных» на карточке и в отчете называет причину: репозиторий пуст,
не удалось прочитать (размер, сбой), нет файлов кода, строки кода не прочитаны,
строки посчитаны прежней версией сборщика, запуски CI не видны или еще идут,
`ci.yaml` не разобран, нет прав на AppSec, мало данных для категории. Причина
выводится из фактов, а не из общего текста.

## 8. Воспроизводимость и версии

- **Версия модели** (`MODEL_VERSION`) записана у каждой оценки. Любая правка,
  меняющая смысл балла (формула, анкер, признак робота, классификация факта), —
  новая версия; при смене версии сервер сам пересчитывает всю историю из
  сохраненных фактов, строки прежних версий не перезаписываются.
- **Версия сборщика** записана у каждого анализа. Репозитории, чей последний
  анализ собран старым сборщиком, ночная волна ставит на повторный анализ
  порциями (по умолчанию 5000 за ночь, по убыванию лайков).
- Оценка считается на дату анализа; одинаковые факты и дата дают одинаковый
  результат.

**Журнал последних версий:**

- `4.3.1-hci` / сборщик 4 (26.09.2026, В5.5 тур 1): пометки техдолга считаются
  только в коде вне тестов (у сканеров пометок счетчик был завышен —
  repo-vitals: 196 вместо 37); «кода нет» — балл категории «Состояние кода» 0
  с причиной вместо «нет данных»; рекомендации с нулевым эффектом не
  выводятся. Живые оценки репозиториев с маркерами в тестах после
  повторного анализа могут вырасти — счетчик долга стал честнее.
- `4.3.0-hci` / сборщик 3 (24.09.2026, В5.3-М): закрытие методики по аудиту
  (тесты как бонус, сжатие малого кода и малой выборки задач, потолки
  «Безопасности», CI без видимых запусков — «нет данных»).

**Контрольные сценарии** (чистый расчет на синтетических фактах, изменение

| Сценарий | Изменение | Вывод |

| ребейз 13 коммитов | 0 | ребейз — не синк |
| 10 задач «открыл и сразу закрыл» | 0 | мгновенные закрытия не в счет |

## 10. Ограничения

| Ограничение | Масштаб | Статус |
|---|---|---|
| Задачи, закрытые через час и больше, засчитываются: 10 фиктивных задач, закрытых через 61 минуту, поднимают пустой трекер | индекс +21,6 | принято (решение 24.09); защита участием второго человека — план развития |
| Лицензия и файлы от 16 символов, строка текста под заголовком README засчитываются | до +19,0 | принято: проверяется наличие содержания, не его смысл |
| Удалить пометку (`TODO` → `T0D0`) дешевле, чем исправить | до +19,7 | принято: любая метрика по пометкам обходится их удалением |
| Сгенерированные данные в формате кода (большой JSON) увеличивают знаменатель плотности | +8,1 | план развития |
| Зеленый пайплайн без проверок (`echo ok`) = CI 100 | полный +18,8 | план развития (содержательность шагов) |
| Коммиты кроном или с подмененными датами наращивают частоту | +10,6 | план развития (частота по активным дням); вход фрод-флаггера |
| Закрытие зависших задач без ответа улучшает «Задачи» | +12,8 | план развития (нужны комментарии закрытых задач) |
| Скрытие канала (отзыв права на CI/AppSec) убирает категорию | полный до +37 | смягчено: берется последний известный факт канала |
| Потолок AppSec снимается статусом «принятый риск»/«ложное срабатывание» | полный +12 | принято: статус — решение владельца репозитория по спецификации AppSec |
| «Нет данных» может дать итог выше худших данных (перенормировка) | до 13 баллов индекса | свойство перенормировки; альтернатива — штрафовать незнание, что противоречит ТЗ |
| Часть оценок до повторного анализа посчитана по фактам старого сборщика (у сборщика до 4 счетчик пометок включал тесты) | переходно, ~6 ночей | досканирование по лайкам |
| Индекс по 4 публичным категориям — CI и Безопасность вне рейтинга | — | указание организаторов (Q&A №1) |
| Граф уязвимостей SCA (цепочка «код → зависимость → уязвимая зависимость») в оценку не входит: SCA-находки считаются в «Безопасности» наравне с находками других движков AppSec, но REST AppSec API графа не отдает — зависимости скана есть только плоским списком, граф — в SBOM-артефактах веб-интерфейса (зонд 25.09) | полный показатель | частично закрыто (Q&A №14); проверка SCA-находки на тестовом репо с уязвимой зависимостью — В5.5 |

## 11. Почему такие числа

- **Веса категорий** — пример ТЗ §3.2; индекс — их пересчет на 4 категории.
- **Порог 0,4** — для индекса это две публичные категории из четырех: оценка по
  одной категории выдавала бы ее за оценку проекта.
- **Потолки 49, 40, 69** привязаны к зонам (70-100 «здоров», 40-69 «требует
  внимания»): открытая high — категория не бывает «здоровой» (69); открытая
  critical — не выше нижней границы «требует внимания» (40); утекший критичный
  секрет — итог не выше середины зоны «требует внимания» (49), то есть никогда
  не «здоров» и не выше типичного непроверенного проекта.
- **Анкеры** откалиброваны по живой выборке каталога (драфт методики,
  приложение А) и заморожены вместе с версией модели.
- **10 задач и 200 строк** — размер выборки, с которого доли перестают
  определяться единичными событиями; **5 пометок** — знаменатель, при котором одна
  старая пометка не обрушивает долю; **16 символов** — короче не бывает
  осмысленного текста лицензии или правил.
- **Внутрикатегорийные веса:** основная метрика категории (свежесть, плотность,
  доля успешных запусков, плотность находок) — наибольший вес; второстепенные
  (корень, релизы, запросы на слияние) — 0,1.

## 12. Метрики ТЗ и механизмы

| Требование ТЗ §3.1 | Механизм |
|---|---|
| Документация: README, лицензия, инструкции запуска, сборки, тестов, CONTRIBUTING, CODEOWNERS | факты git: файлы корня и разделы README (§4.1) |
| CI/CD: наличие, статусы, частота успехов, длительность, стабильность | `ci.yaml` + запуски REST (§4.5); стабильность — доля успеха, взвешенная по свежести |
| Безопасность: SAST/SCA/секреты, критичность, статус исправления | AppSec SourceCraft (§4.6), без своего сканирования |
| Активность: коммиты, частота, последняя активность, авторы, запросы на слияние, релизы | история git + REST (§4.2) |
| Задачи: открытые/закрытые, зависшие, время ответа и закрытия | REST (§4.3) |
| Состояние кода: TODO/FIXME, количество, давность, техдолг | git + blame (§4.4), плюс тесты как бонус |
