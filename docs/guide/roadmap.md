# План развития

HealthCraft развивается в 4 направлениях, и разделы ниже идут в порядке приоритета.

## Развитие методики оценки

- Состояние кода дополнят статические анализаторы для всех языков репозитория: сложность функций, доля дублирования, покрытие тестами из артефактов CI и результаты линтеров. Владелец увидит, какие файлы снижают оценку. Сейчас категория строится на плотности и возрасте пометок TODO и FIXME, доле тестов и числе записей в корне репозитория; ее состав описан в разделе [Состояние кода](method/metrics.md#code).
- HealthCraft научится различать в CI шаги с тестами, сборкой и проверками, и пайплайн, который проверяет каждое изменение, получит более высокую оценку. Сейчас по конфигурации проверяется только наличие `ci.yaml` хотя бы с одним шагом, а остальное дают результаты запусков. Как CI/CD оценивается сейчас, описано в разделе [CI/CD](method/metrics.md#cicd).
- Частота коммитов будет считаться по активным дням, чтобы [Активность](method/metrics.md#activity) точнее показывала, насколько ровно команда работает над проектом. Сейчас подметрика считает число коммитов в месяц.
- В категории Задачи начнут учитываться закрытие с участием второго человека и ответы в закрытых задачах. Выше оценку получат проекты, где на задачи отвечают по существу. Сейчас число задач, закрытых не их автором, уже собирается в факт `issues.stats`, но в балл не входит, а время до первого ответа считается только по 50 самым свежим открытым задачам; текущие правила – в разделе [Задачи](method/metrics.md#issues).
- Граф зависимостей расширится на другие пакетные менеджеры: сейчас уязвимость в прямой и транзитивной зависимости различается по `package-lock.json` и `npm-shrinkwrap.json` версий 2 и 3 и по `pnpm-lock.yaml` начиная с версии 6, следующие – `yarn.lock`, `poetry.lock`, `Cargo.lock` и `go.sum`. Рекомендация дополнительно назовет версию, до которой обновить пакет, когда AppSec начнет ее отдавать. Как считается категория сейчас, описано в разделе [Безопасность](method/metrics.md#security).
- HealthCraft научится распознавать вендорные зависимости, скопированные в репозиторий. Их уязвимости и устаревшие версии он покажет отдельно, а Состояние кода будет описывать собственный код проекта. Сейчас каталоги `vendor` и `node_modules` пропускаются только при чтении манифестов и lock-файлов, а в строки кода и пометки TODO такие файлы входят.
- Веса категорий и подметрик будут уточняться по накопленной истории оценок. Каждое уточнение выйдет новой версией модели оценки. Пересчет сохраненных фактов новой версией уже работает: при старте сервера и скриптом `scripts/rescore-m4.ts`, по правилам из раздела [Воспроизводимость и версии](method/scores.md#versii).

## AI-возможности

- Каждое число в AI-обзоре будет открывать факт анализа, из которого оно взято, так же как сейчас это делает кнопка [[Источник данных]] у рекомендации. Сейчас привязки к фактам проверяются и сохраняются вместе с текстом, но на карточке текст показывается без ссылок. Как тексты модели привязаны к фактам сегодня, описано в разделе [Привязка к фактам и проверка](data/ai.md#proverka-faktami).
- AI-рекомендация будет предлагать готовое изменение, например предложение изменений с заготовкой файла, дополненной под репозиторий. Заготовки для документации уже есть в рекомендациях и собираются из фактов анализа без языковой модели, они описаны в разделе [Заготовки файлов](method/recommendations.md#zagotovki).
- Руководитель получит 1 обзор по всем репозиториям организации: где риски и что исправить в первую очередь. Сейчас раздел [[repos:Мои репозитории]] группирует репозитории по организациям и показывает по каждой число оцененных и число репозиториев в каждой зоне, как описано в разделе [Анализ своего репозитория](quickstart.md#own).
- На карточке можно будет задать вопрос языковой модели и получить ответ со ссылками на факты.

## Интеграция с SourceCraft

SourceCraft получит встроенную оценку здоровья репозиториев, а команды – подсказки там, где они работают каждый день.

- Оценка появится на странице репозитория SourceCraft рядом с его описанием.
- Шаг CI «проверка здоровья» посчитает оценку в пайплайне SourceCraft, а порог оценки станет условием слияния предложения изменений.
- Рекомендация с заготовкой файла сама откроет предложение изменений в репозитории. Сейчас заготовка скачивается файлом, а предложение изменений владелец открывает сам.
- О падении оценки или смене зоны владелец узнает из уведомления сразу после анализа.
- Руководитель увидит общую оценку организации и сможет сравнить команды между собой.
- Команда SourceCraft CLI покажет оценку в терминале, а MCP-сервер HealthCraft откроет агентам и SourceCraft Code Assistant оценку, факты и рекомендации.
- Владелец закрытого репозитория сможет перевыпустить ключ бейджа одной кнопкой: прежняя ссылка перестанет открывать бейдж, остальные репозитории не затронет. Сейчас ключ выводится из секрета сервера и адреса репозитория, и отдельно для одного репозитория его не сменить.
- По персональному токену участника API будет отдавать полный Repo Health Score с CI/CD и Безопасностью. Сейчас публичный API не принимает токен и отдает только HealthCraft Index по открытым категориям, как описано на странице [Бейдж и публичный API](guide/badge-api.md).

## Масштабирование

- База и очередь переедут на сетевую СУБД, а обработчики анализов будут работать на нескольких машинах. Тогда каталог и число пользователей смогут расти без смены сервера; текущая схема с 1 базой SQLite и процессами `web` и `rating` на одной машине описана в разделе [Масштабирование](ops/scaling.md#masshtabirovanie).
- Все процессы будут делить единые квоты запросов к SourceCraft, и нагрузка на платформу останется в заданных пределах при любом числе обработчиков. Сейчас интервал между запросами и бюджет соблюдает каждый процесс отдельно. Действующие бюджеты перечислены в разделе [Бюджеты и повторы запросов](data/sources.md#byudzhety).
- Повторный анализ будет обрабатывать только новые коммиты, поэтому оценка станет обновляться быстрее, а клон и запросы займут меньше ресурсов. Сейчас каждый анализ клонирует репозиторий заново, у крупных репозиториев с усечением истории по дате, и только AI-обзор, поставленный в очередь сразу за анализом, получает его клон без повторного клонирования.
