# Развертывание и настройка

HealthCraft разворачивается на 1 виртуальной машине: 2 процесса сервиса и прокси с HTTPS работают в контейнерах Docker Compose. Код выкладывается скриптом `deploy/deploy.sh` с машины разработчика, а образ собирается на самой ВМ. Секреты и база хранятся на ВМ, и выкладка их не затрагивает.

## Что нужно

Для развертывания понадобятся:

- ВМ с Ubuntu 24.04: 4 vCPU, 8 ГБ памяти, SSD 64 ГБ, статический IP. На такой конфигурации работает https://health-craft.ru.
- Входящие TCP 22, 80 и 443 в группе безопасности или файрволе.
- Домен: A-записи основного домена и `www` указывают на IP ВМ.
- Доступ к ВМ по SSH-ключу.
- На машине разработчика – bash, git, ssh и клон репозитория HealthCraft.

## Подготовка ВМ {#podgotovka}

Подготовка выполняется 1 раз. Чтобы подготовить ВМ:

1. Установите Docker с Compose v2, а также `sqlite3` и `zstd` для резервных копий.
   ```bash
   sudo apt update && sudo apt install -y docker.io docker-compose-v2 sqlite3 zstd
   ```
2. Добавьте пользователя в группу `docker`. Изменение действует после повторного входа по SSH.
   ```bash
   sudo usermod -aG docker "$USER"
   ```
3. Создайте рабочий каталог `/srv/healthcraft`, владелец – ваш пользователь.
   ```bash
   sudo install -d -o "$USER" /srv/healthcraft
   ```
4. Создайте файл подкачки на 4 ГБ и включите его при загрузке.
   ```bash
   sudo fallocate -l 4G /swapfile && sudo chmod 600 /swapfile && sudo mkswap /swapfile && sudo swapon /swapfile && echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab
   ```

## Настройки {#nastroyki}

Все настройки HealthCraft задаются переменными окружения. При запуске из исходников сервис читает `.env` в текущем каталоге, причем переменная окружения процесса важнее строки в файле. В контейнерах файл `.env` из рабочего каталога `HC_DIR` передает сервису Docker Compose. Полный список с пояснениями и значениями по умолчанию есть в файле `.env.example` в корне репозитория.

Чтобы создать настройки на ВМ:

1. На машине разработчика скопируйте `.env.example` на ВМ.
   ```bash
   scp .env.example <user>@<IP ВМ>:/srv/healthcraft/.env
   ```
2. На ВМ закройте файл от других пользователей.
   ```bash
   chmod 600 /srv/healthcraft/.env
   ```
3. Впишите `SOURCECRAFT_TOKEN` – персональный токен SourceCraft. Это единственная обязательная переменная: без нее обход каталога и периодические анализы не запускаются, а в ответе `/api/health` поле `reasons` сообщит, что у планировщика нет серверного токена SourceCraft.
4. Если нужны вход и AI, впишите их переменные из таблицы ниже.
5. Добавьте адрес сервиса. Например, для домена `hc.example.com`:
   ```ini
   SITE_ADDRESS=hc.example.com, www.hc.example.com
   CANONICAL_HOST=hc.example.com
   PUBLIC_BASE_URL=https://hc.example.com
   YA_REDIRECT_URI=https://hc.example.com/auth/ya/callback
   ```
6. Добавьте адрес из `YA_REDIRECT_URI` в OAuth-приложение Яндекс ID.

Сертификат HTTPS прокси Caddy выпускает и продлевает сам. Время в переменных задается в миллисекундах, а переключатели принимают `true` или `false`, `1` или `0`. Не задавайте в `.env` переменные `PROCESS_ROLE`, `PORT`, `SCAN_MIN_FREE_MB` и `DATA_DIR`, потому что их задают `deploy/compose.yaml` и образ.

| Переменная | По умолчанию | Что задает |
|---|---|---|
| `APP_SECRET` | – | ключ подписи сессий и шифрования токенов пользователей, не короче 32 символов; без него вход выключен. Создать: `openssl rand -hex 32` |
| `YA_CLIENT_ID`, `YA_CLIENT_SECRET` | – | OAuth-приложение Яндекс ID; без них вход отвечает 503 |
| `YA_REDIRECT_URI` | `http://localhost:8418/auth/ya/callback` | адрес возврата после входа, как в OAuth-приложении |
| `PUBLIC_BASE_URL` | адрес из `YA_REDIRECT_URI` | публичный адрес сервиса для кода бейджа |
| `LLM_PROVIDER` | `yandex` | провайдер модели: `yandex` (YandexGPT) или `zai` (z.ai); провайдер один, выбирается этой настройкой |
| `MAIN_MODEL` | `yandexgpt` | модель; для `zai` по умолчанию `glm-5.3` |
| `YAGPT_API_KEY`, `YAGPT_FOLDER_ID` | – | API-ключ сервисного аккаунта и ID каталога Yandex Cloud; без ключа модели AI-обзор недоступен |
| `ZAI_API_KEY` | – | ключ z.ai, если `LLM_PROVIDER=zai` |
| `AI_OVERVIEW_PER_HOUR`, `AI_OVERVIEW_PER_DAY` | 2, 6 | AI-обзоров на человека в час и в сутки |
| `AI_CHECK_PER_HOUR`, `AI_CHECK_PER_DAY` | 5, 20 | проверок оценки на человека в час и в сутки |
| `AI_UNLOCK_PASSWORD` | – | пароль снятия личных лимитов AI, не короче 20 символов; нужен `APP_SECRET` |
| `AI_TOP_AUTO` | `0` | `1` – готовить обзор и проверку для топа рейтинга после нового анализа |
| `QUEUE_USER_SCANS_PER_HOUR`, `QUEUE_USER_ACTIVE_MAX` | 10, 2 | запусков анализа на пользователя в час и одновременно |
| `QUEUE_FAVORITES_MAX`, `QUEUE_FAVORITE_CHECKS_PER_MINUTE` | 500, 6 | репозиториев в избранном и добавлений в избранное в минуту |
| `QUEUE_CARD_PER_MINUTE` | 30 | открытий карточки, отчета или заготовки в минуту от вошедшего пользователя |
| `SITE_ADDRESS` | не задан – только HTTP | домены для HTTPS через запятую |
| `CANONICAL_HOST`, `STAND_IP` | – | основной домен и IP машины: остальные адреса переадресуются на домен |
| `HC_DIR` | `/srv/healthcraft` | рабочий каталог контейнеров: `.env`, `data/`, `tmp/` |
| `HTTP_PORT`, `HTTPS_PORT` | 80, 443 | порты прокси на машине |

Переменные ролей и очереди описаны на странице [Архитектура](architecture.md), а переменные расписания и бюджетов анализа – на странице [Периодический анализ и масштабирование](scaling.md).

{% note warning %}

Не меняйте `APP_SECRET` на работающем сервисе. Со старым ключом пропадут все сессии, а сохраненные персональные токены пользователей нельзя будет расшифровать: пользователям придется войти и сохранить токен заново.

{% endnote %}

## Выкладка

Чтобы выложить новую версию, на машине разработчика выполните в каталоге репозитория:

```bash
deploy/deploy.sh <user>@<IP ВМ>
```

Скрипт упаковывает код закоммиченного `HEAD` без `.env`, `data/` и зависимостей и распаковывает его в `/srv/healthcraft/app`, а прошлая версия остается в `/srv/healthcraft/app.prev`. Затем он собирает образ на ВМ, пересоздает контейнеры командой `docker compose ... up -d --build`, перезапускает прокси и печатает состояние контейнеров.

Незакоммиченные изменения на ВМ не попадают: скрипт предупредит о них. Ключ SSH задает переменная `HC_SSH_KEY`, по умолчанию `~/.ssh/healthcraft-stand`. Чтобы откатиться, переключитесь в репозитории на нужный коммит и снова запустите `deploy/deploy.sh`.

## Изменение настроек {#izmenit-nastroyki}

Чтобы применить новые значения в `/srv/healthcraft/.env`:

1. Отредактируйте `/srv/healthcraft/.env` на ВМ.
2. Перейдите в каталог кода.
   ```bash
   cd /srv/healthcraft/app
   ```
3. Пересоздайте контейнеры.
   ```bash
   docker compose --env-file /srv/healthcraft/.env -f deploy/compose.yaml up -d
   ```

Команда `docker compose restart` не перечитывает `.env`: контейнер перезапустится со старыми значениями.

## Резервные копии {#backup}

Скрипт `deploy/backup.sh` копирует работающую базу без остановки сервиса, проверяет и сжимает копию и хранит 3 последние копии в `/srv/healthcraft/backups`. Запускайте его по расписанию через `crontab -e`.

Чтобы восстановить базу:

1. Остановите `web` и `rating`.
2. Распакуйте копию командой `zstd -d` на место `/srv/healthcraft/data/repo-health.db`.
3. Удалите файлы `-wal` и `-shm` рядом с базой.
4. Снова запустите контейнеры.

## Проверка состояния {#sostoyanie}

Состояние сервиса отдает `GET /api/health`:

```bash
curl https://hc.example.com/api/health
```

HTTP-статус ответа всегда 200, поэтому состояние определяйте по телу ответа. Поле `ok` равно `true`, когда очереди анализа обслуживаются, а обход каталога и пересчет оценок идут без ошибок. Пока после выкладки новой версии модели идет пересчет оценок, `ok` равно `false`. Если `ok` равно `false`, массив `reasons` перечисляет, что не так: например, нет токена SourceCraft, обход каталога давно не удается или задание зависло. Вот фрагмент ответа с выдуманными числами:

```json
{
  "ok": true,
  "reasons": [],
  "repos": 1250,
  "queue": { "user": 0, "rating": 14 },
  "failedJobs24h": 3,
  "lastReconcileAt": "2026-09-15T09:05:12.418Z",
  "freshAsOf": "2026-09-15T09:07:55.102Z"
}
```

В поле `queue` – заявки в очереди и в работе, в `failedJobs24h` – неудачные заявки за сутки. Поле `lastReconcileAt` хранит время последней успешной сверки каталога, а `freshAsOf` – время последнего завершенного анализа с оценкой.

Docker отмечает контейнер `web` как healthy, как только сервер отвечает, а работу очередей и обхода каталога показывает только поле `ok`. Поэтому для контроля состояния следите за телом ответа.
