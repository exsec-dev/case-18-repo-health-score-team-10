# Архитектура

HealthCraft – один сервис на Bun и TypeScript, который работает в 2 процессах с общей базой SQLite. Процесс `web` обслуживает сайт и заявки пользователей, процесс `rating` обходит каталог SourceCraft и обновляет рейтинг. Перед ними стоит прокси Caddy с HTTPS.

## Схема

```text
                    браузер, README с бейджем
                               |
                   caddy: HTTPS, заголовки защиты
                               |
    +--------------------------+     +---------------------------------+
    | web                      |     | rating                          |
    | сайт и API, вход Я ID,   |     | обход каталога, плановые        |
    | анализы по заявкам,      |     | анализы, пересчет оценок,       |
    | AI-обзоры и проверки     |     | AI для топа рейтинга            |
    +------------+-------------+     +----------------+----------------+
                 |                                    |
                 +------> SQLite (WAL): факты, <------+
                          оценки, очередь заявок

  внешние сервисы: SourceCraft REST API, AppSec API, git-клоны
                   (временный каталог), Яндекс ID, YandexGPT
```

## Компоненты

| Компонент | Что делает |
|---|---|
| `caddy` | HTTPS с сертификатом Let's Encrypt, заголовки защиты, адрес клиента для лимитов. Единственный компонент с портами наружу: 80 и 443 |
| `web` | сайт и API, вход через Яндекс ID, анализы по заявкам пользователей, AI-обзоры и проверки оценки |
| `rating` | сверка каталога, плановые анализы, суточный снимок мест рейтинга, пересчет оценок после смены модели, AI-тексты для топа рейтинга при `AI_TOP_AUTO=1` |
| SQLite в режиме WAL | факты, оценки, рекомендации, очередь заявок, пользователи, зашифрованные токены, AI-тексты |
| Временный каталог | клоны репозиториев на время анализа, у каждого процесса свой |

Внешние сервисы – SourceCraft REST API, AppSec API и git-хост SourceCraft, Яндекс ID для входа и YandexGPT для AI-текстов. Что берется из каждого источника – на странице [Источники данных](../data/sources.md).

## Роли процессов

Роль задает переменная `PROCESS_ROLE`. Образ и код у ролей общие.

| Роль | Что запускает |
|---|---|
| `web` | сайт и API, циклы пользовательских заявок |
| `rating` | планировщик обхода каталога, циклы плановых анализов, пересчет оценок |
| `all` | все в одном процессе. Значение по умолчанию, для разработки |

В контейнерах `rating` стартует после того, как `web` прошел проверку здоровья, и получает меньшую долю процессора. Плановая волна анализов поэтому не замедляет сайт. Раз в час оба процесса выполняют обслуживание: закрывают зависшие анализы, удаляют старые заявки и забытые клоны.

## Путь данных

1. Заявка на анализ попадает в очередь: пользователь нажал [[Обновить анализ]] или планировщик нашел новый либо изменившийся репозиторий.
2. Свободный цикл процесса берет заявку.
3. Анализ клонирует репозиторий и запрашивает REST API, а с персональным токеном автора заявки – еще и AppSec API.
4. Факты записываются в базу, клон удаляется.
5. Код считает оценки и рекомендации. Статус анализа, оценки и рекомендации записываются одной транзакцией.
6. Карточка, рейтинг, отчеты Markdown и PDF и публичный API читают сохраненные данные.

AI-обзор – отдельная заявка. Она работает с фактами последнего завершенного анализа и оценку не меняет.

## Очередь заявок {#ochered}

Заявки хранятся в таблице `jobs` той же базы. Есть 2 полосы: пользовательская и рейтинга, и 3 рода заявок: анализ, AI-обзор, проверка оценки. У каждой пары «полоса × род» свои циклы-исполнители:

| Цикл | Сколько параллельно | Переменная |
|---|---:|---|
| Анализы пользователей | 2 (от 1 до 8) | `QUEUE_USER_SCAN_SLOTS` |
| AI-обзоры пользователей | 2 (от 1 до 8) | `QUEUE_USER_AI_SLOTS` |
| Проверки оценки | 1 на полосу | – |
| Плановые анализы и AI для топа | 1 на род | – |

Заявки берутся с арендой:

- Цикл забирает заявку одной командой `UPDATE`, поэтому двум циклам одна заявка не достанется.
- Аренда длится 10 мин (`SCHEDULER_LEASE_MS`), работающий цикл продлевает ее каждые 3 мин 20 с.
- При штатной остановке процесс закрывает прерванные анализы как сбойные, возвращает свои заявки в очередь и гасит процессы git. Попытка при этом не тратится.
- Если процесс упал, аренда истекает, и заявку берет другой цикл. После 3 попыток (`QUEUE_MAX_ATTEMPTS`) заявка завершается с причиной [[превышено число попыток]].

В пользовательской полосе заявки разных людей идут по кругу. Вторая заявка того же человека ждет чужие, но свободный цикл не простаивает. Репозиторий, анализ которого уже шел дольше 5 мин (`QUEUE_HEAVY_SCAN_MS`), берет только первый цикл. Остальные в это время обслуживают небольшие репозитории.

## Стек

- Bun 1.4.2 и TypeScript в строгом режиме;
- SQLite через `bun:sqlite`;
- React 19 и Gravity UI (`@gravity-ui/uikit` 7.49.0);
- pdfmake 0.3.11 для отчетов PDF;
- YandexGPT, резервный провайдер – z.ai;
- git 2.31 или новее;
- Docker Compose и Caddy 2.10.
